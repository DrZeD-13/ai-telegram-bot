## Why

Порты Telegram и нейросети уже есть, как и сущность входящего сообщения, но бот ещё не обрабатывает очередь: не забирает новые апдейты, не отвечает моделью и не фиксирует исход в БД. Нужен прикладной сценарий, который связывает poll, валидацию, AI и ответ пользователю.

## What Changes

- Добавить application-сервис обработки входящих сообщений Telegram: взять курсор из БД, запросить новые сообщения, обработать пачками по 100, зафиксировать пачку одним `flush` Unit of Work после цикла по чанку.
- Валидировать длину текста запроса (не больше 1024 символов); при успехе отправить текст в нейросеть через `NeuralNetworkGateway` с суффиксом «ответ сделай не больше 1024 символа» и вернуть ответ в чат.
- При ошибке валидации, сбое нейросети или недоставке ответа в Telegram сохранить запись со статусом «обработано с ошибкой» (текст пользователя обрезать до 1024 символов) и отправить в чат фиксированное сообщение по типу ошибки.
- Успешная доставка ответа модели — запись со статусом «обработано успешно».
- Добавить read-only доменный интерфейс репозитория `App\Domain\Repository\ProcessedTelegramMessageRepository` (только чтение курсора и дубликатов) и порт Unit of Work для постановки сущностей в unit of work и одного commit на чанк. Консольная команда запускает poll. Убрать `save` с Doctrine-репозитория: репозиторий не пишет в БД.
- Хранить Telegram `update_id` у записи, чтобы offset `getUpdates` соответствовал Bot API (последний обработанный update id + 1), а не `message_id` чата и не суррогатному PK.

## Capabilities

### New Capabilities

- `telegram-ai-inbound-processing`: poll входящих сообщений, валидация длины, вызов нейросети, ответ в чат, статусы успеха/ошибки, пакетное сохранение, пользовательские тексты ошибок.

### Modified Capabilities

- (нет)

## Impact

- Application: use case, порт Unit of Work, константы лимита и текстов ошибок.
- Domain: read-only интерфейс `App\Domain\Repository\ProcessedTelegramMessageRepository`; поле `update_id` у `ProcessedTelegramMessage` (миграция); инварианты обрезки текста при ошибке остаются в сценарии.
- Infrastructure: реализация read-only репозитория (курсор, поиск по chat+message); реализация Unit of Work над Doctrine EntityManager; удалить `save` у репозитория.
- Presentation: консольная команда, вызывающая use case.
- Внешние системы: Telegram Bot API (`getMessages` / `sendMessage`), нейросеть (`createChatCompletion`).
- Тесты: unit на use case (ветки успеха и 2.1) по `docs/testing.md`.
- Вне scope: webhook, очередь Messenger, история диалога, обрезка ответа модели, несколько провайдеров AI.
